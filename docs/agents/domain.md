# 领域与架构文档使用指引 (Domain Docs)

本文件规定智能体工程技能在探索与维护本仓库代码时，如何读取与消费领域与架构决策文档。

## 探索代码库前的前置阅读 (Before exploring, read these)

- 根目录下的 **`CONTEXT.md`**：记录核心领域术语、通用语言与上下文边界。
- **`docs/adr/`** 目录：记录系统架构决策记录（Architecture Decision Records）。阅读与当前工作任务相关的决策。

若上述文件或目录尚不存在，**静默推进任务**。切勿主动报错，切勿无意义地建议提前创建。`/domain-modeling` 技能（通过 `/grill-with-docs` 或 `/improve-codebase-architecture` 触发）会在实际解决领域术语或重大架构决策时懒加载创建它们。

## 目录结构布局 (File structure)

单一上下文项目布局（适用于本仓库）：

```
/
├── CONTEXT.md       # 领域术语表与统一语言
├── docs/adr/        # 架构决策记录 (ADR)
└── src/             # 业务源码
```

## 严格遵循术语表词汇 (Use the glossary's vocabulary)

当交付物或代码中涉及领域概念时（包括工单标题、重构方案、假设推演、单元测试命名等），必须严格使用 `CONTEXT.md` 中定义的标准术语，严禁擅自使用未经定义的同义词。

如果所需的领域概念在术语表中尚未收录，应视为信号：要么是在随意创造本项目不存在的自造词（应重新评估），要么是领域模型存在真实缺口（记下该缺口供 `/domain-modeling` 梳理）。

## 显式标注 ADR 冲突 (Flag ADR conflicts)

如果当前方案或代码实现与既有的 ADR 产生冲突，必须显式在输出中高亮披露，严禁静默覆盖既定决策：

> *与 ADR-0002 产生冲突——建议重新审议该决策，原因在于……*
