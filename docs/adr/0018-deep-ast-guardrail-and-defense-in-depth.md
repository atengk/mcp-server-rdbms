# 0018: 深度 AST 语法守卫强化与纵深防御架构

## 背景与痛点

在基于 LLM 的自主数据库操作演进过程中，原有的 AST 安全检测在应对复杂与极端 SQL 场景时显现出深层盲区：
1. **恒真条件穿透**：大模型生成的 SQL 可能包含伪装条件（如单纯的 `WHERE 1=1` 或 `WHERE true`），旧有机制仅校验 `WHERE is not None`，仍会导致灾难性的全表数据覆写或清除；
2. **锁读语句隐性危害**：`SELECT ... FOR UPDATE` 虽属于查询语法，但在无状态的 MCP 交互中可能导致连接池死锁或排他行锁长时间挂起，并在只读从库直接报错；
3. **复合写入支持断层**：主流企业级数据库广泛使用的 `MERGE INTO` / `REPLACE INTO` 复合写语法，因未被收纳于基础 DML 原语白名单而被硬性误杀；
4. **副作用函数静态穿透**：诸如 `pg_sleep`（拒绝服务）、`nextval`（序列污染）或管理运维函数，因属于 `SELECT func()` 形式而能穿透常规只读白名单。

## 架构决策

我们决定对 `ASTGuard` 与系统安全模型实施深度强化，构建静态结构校验与数据库权限联动的纵深防御体系：

1. **恒真条件退化判定 (Trivial WHERE Guard)**：
   - 深入分析 `WHERE` 表达式语法树。仅当整棵表达式完全退化为恒真表达式（如裸字面量 `1=1`、`true`、`'a'='a'` 或纯 `OR` 恒真组合）时触发安全拦截；
   - 宽容保留包含真实业务列过滤的动态 SQL 拼接（如 `WHERE 1=1 AND status = 'inactive'`），兼顾安全性与工业界拼接习惯。
2. **锁读语句全局熔断 (Locking Reads Disallowed)**：
   - 全 MCP 工具链彻底禁止显式 `FOR UPDATE` 与 `FOR SHARE` 锁读语法；
   - 引导大模型全面采纳基于版本号的乐观并发控制（Optimistic Concurrency Control），杜绝长事务排他锁隐患。
3. **复合写操作纳管与关联守卫 (Composite Mutation Guard)**：
   - 将 `exp.Merge` 纳入 `sql_dml` 允许名单；
   - 强制前置校验 `MERGE` 的 `ON` 关联条件必须非空且非恒真（严禁 `ON 1=1`），并对其内部匹配更新/删除分支实施同等条件的严密审计。
4. **高危函数黑名单与纵深防御架构 (Defense-in-Depth)**：
   - 在 `sql_query` AST 遍历中注入首期高危函数黑名单：覆盖延时与 DoS（`pg_sleep`, `sleep`, `waitfor delay`）、状态变更（`nextval`, `setval`）与连接运维（`pg_terminate_backend` 等）；
   - 正式确立安全职责分界：AST Guardrail 定位于语法结构防御，数据库端底层权限（如分配只读用户并收回存储函数执行权）构成第二道不可替代的运行时纵深防御屏障。

## 收益与结果

- 彻底阻断了借助 `WHERE 1=1` 恶意绕过全表防误删护栏的通道；
- 杜绝了无状态 Agent 滥用排他锁导致的生产并发雪崩；
- 扩展了企业级方言的高性能 Upsert 能力，同时建立了严密的多层级防御标准。
